# CompiledSchema のメモリ割り当て戦略

## 目的

CompiledSchema.compile() が内部で ArenaAllocator を暗黙的に使用している設計について、変更すべきか、どう改善すべきかを多角的に検討する。

## 視点

### Zig エコシステムの設計哲学

- 内部 Arena は「制御の剥奪」ではなく「実装詳細の適切な隠蔽」。CompiledSchema が内部リソースの管理手段として Arena を所有するのは、ArrayList が内部で alloc/resize する戦略を隠すのと同じ
- `std.json.parseFromSlice` が全く同じパターン（allocator を受け取り、内部で arena を作り、deinit で一括解放）を採用しており、Zig 標準ライブラリが確立した慣例に一致する
- 「明示は暗黙に勝る」は制御フローや副作用の隠蔽を禁じる原則であり、内部のアロケータ戦略まで露出せよという意味ではない
- ただし将来的にユーザーが外部 Arena を渡して複数スキーマのライフタイムを統合したいケースはあり得る。その場合は必要になった時点で `compileInto(arena)` のような専用エントリポイントを追加すればよい

### API ユーザビリティ

- 現在の API は「正しい使い方が最も簡単な使い方」（pit of success）になっている。compile して deinit するだけ
- Arena を外に出すと、全ユーザーに Arena のライフタイム管理という認知負荷を強制する。deinit 内部の regfree → arena.deinit の順序依存も漏洩する
- 「完全な制御」を求めるユーザーは少数派。典型的ユースケースでは「正しく動くこと」と「リソースが最終的に解放されること」が重要であり、個々のアロケーションの制御ではない
- 「暗黙の動作」という指摘には一理ある。パラメータ名とドキュメントで Arena の存在を明示すれば、暗黙ではなく「文書化された内部実装」になる

### パフォーマンス

- Arena をやめて個別 malloc にすると compile が 2-5 倍遅化する見込み。openapi で 177ms → 最悪 885ms。競合優位の大半を失う
- メモリ無駄率 27-33% は絶対量で KB 単位（最大 104KB）。個別 malloc のメタデータオーバーヘッド（1 alloc あたり 16-32 bytes × 数百ノード）を考えると、ノード数が多い場合は Arena の方がメモリ効率が良い可能性すらある
- 「観測すらできない」問題は memoryUsage() だけでは不十分。arena の requested bytes vs allocated bytes（断片化率）を返す API を併設すべき。観測できないものは改善できない

### OSS 保守性

- pre-1.0 だからこそ API 表面を最小に保つべき。追加は容易だが削除は困難
- CompileOptions による arena 戦略選択は不要。確保戦略を外部に露出させると将来の内部最適化を阻害する
- 観測 API（memoryUsage）は読み取り専用で保守コストが低い。v1.0 前に入れる価値がある。ベンチマーク・チューニングのフィードバックループを回すために計測手段は先に確保しておくべき

## 提案

### 全員一致で推奨

1. **内部 ArenaAllocator は維持する。** compile のユースケース（大量の同寿命オブジェクト、個別解放不要、deinit で一括解放）は Arena の教科書的な適用例であり、2-5 倍の速度優位を生み出している
2. **パラメータ名を `child_allocator` → `allocator` に変更する。** 現在の名前は ArenaAllocator の内部実装を API 表面に漏らしている。`std.json.parseFromSlice` と同じ `allocator` が適切
3. **ドキュメントで Arena の使用を明示する。** doc comment に「内部で ArenaAllocator を使用する」と記載し、暗黙ではなく文書化された設計にする

### 条件付き推奨

4. **`memoryUsage()` 観測 API を追加する。** arena の使用量・確保量・ノード数を返す読み取り専用 API。保守コストが低く、ユーザーにメモリ挙動の透明性を提供する。v1.0 前に計測手段を確保しておくことで、将来の最適化判断の土台になる

### 推奨しない

5. **CompileOptions で arena を外から渡す API は追加しない。** 現時点では YAGNI。実際のユーザー要求が issue で複数報告されてから検討すべき。追加する場合は `compileInto(arena)` のような別関数として、デフォルト API を複雑にしない形で提供する

### トレードオフの整理

| 選択肢 | 速度 | メモリ効率 | API 簡潔さ | 保守コスト |
|---|---|---|---|---|
| 現状維持 (内部 arena) | 最速 | 最大33%無駄 | 最も簡潔 | 最小 |
| arena を外から渡せる | 同等 | ユーザー次第 | 複雑化 | 中 |
| arena をやめる | 2-5倍遅化 | 最良 | 複雑化 | 高 |
| **推奨: 現状維持 + 観測API** | **最速** | **最大33%無駄（観測可能）** | **簡潔** | **低** |
