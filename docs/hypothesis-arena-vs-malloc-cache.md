# 仮説: Arena vs 個別 malloc のキャッシュ影響が小さい理由

## 仮説

CompiledSchema のメモリ配置を arena (連続) から個別 malloc (散在) に変えても、warm validation の性能差は小さい。理由は L2 キャッシュが十分大きいため。

## 論拠

- arena (連続): データが RAM 上で隣接 → L1 キャッシュに効率よく載る
- 個別 malloc (散在): データが RAM 上でバラバラ → L1 キャッシュラインごとに別々にフェッチ
- ただし、どちらも一度読んだデータは L2 に残る
- L2 が 16MB あるため、223KB 程度の compiled schema は全部 L2 に入る
- 差は L1 ヒット (~1ns) vs L2 ヒット (~5ns) の違いだけ。RAM (~100ns) まで落ちることは両方ともない
- validation はポインタで木構造を辿る処理のため、アクセス順序は連続ではなくバラバラ。arena の連続配置の恩恵が出にくい

## 実測 (Apple M4 Pro, L1=128KB, L2=16MB)

| Dataset | Arena サイズ | キャッシュ汚染テストでの性能差 |
|---|---|---|
| helm-chart-lock | 5 KB (L1に入る) | +59% |
| openapi | 223 KB (L1に入らない、L2に入る) | +0.8% |
| tsconfig | 218 KB (同上) | +8.8% |
| cspell | 217 KB (同上) | +7.1% |

## 補足

- Rust jsonschema は個別ヒープ確保 (Box, Vec, Arc) で arena を使っていないが、warm で実用的な速度を出している。これは上記仮説と整合する
- キャッシュ汚染テストは 8MB のゴミデータで L1/L2 を汚す方式。L2 (16MB) を完全に汚しきれていない可能性があり、実際の差はもう少し大きいかもしれない
- この仮説が正しければ、arena のメリットは主に compile 速度 (cold) であり、warm にはほぼ寄与しない

## 検証結果

### 第1回テスト (不正確)

ゴミデータの書き込み時間を計測に含めてしまい、全データセットで約 6 秒の固定オーバーヘッドが validation 時間に上乗せされた。結果は無効。

### 第2回テスト (修正版)

ゴミデータ書き込みを計測から除外し、validation 時間のみを比較:

| Dataset | Arena サイズ | L1 flush (256KB) | L1+L2 flush (32MB) |
|---|---|---|---|
| helm-chart-lock | 5 KB | +2.5% | +13.8% |
| openapi | 223 KB | +2.3% | +3.3% |
| tsconfig | 218 KB | +0.7% | +2.3% |
| cspell | 217 KB | +0.1% | +1.6% |

**仮説は概ね正しかった。** L1+L2 を完全に吹き飛ばしても warm への影響は 1.6〜13.8%。小さいスキーマ (helm-chart-lock, 5KB) で最大の影響、大きいスキーマ (openapi, 223KB) で最小。

## 結論

- arena の連続配置による warm 性能への寄与は最大でも約 14% (小スキーマ)、大スキーマでは 2-3% 程度
- 個別 malloc にしても warm 性能はほぼ維持される可能性が高い
- arena のメリットは主に compile 速度 (cold) と deinit の安全性・単純性

## 未検証

- 個別 malloc 版を実装して直接比較する実験はまだ行っていない
- CPU アーキテクチャが異なるマシン (Intel, smaller L2) での挙動は未確認
- 個別 malloc でメモリが実際にどの程度散在するか (malloc の内部実装依存)
